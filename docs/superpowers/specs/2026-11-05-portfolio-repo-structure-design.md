# 作品集 GitHub 目錄架構設計

日期：2026-11-05　｜　狀態：已核准（使用者 2026-11-05）

## 1. User Story

- 身為**正在篩選 AI 產品經理候選人的招募人員**，我想要**打開廖煒立的 GitHub 首頁，30 秒內看到他的定位、最能代表他的作品和聯絡方式**，以達成**判斷是否值得安排面試**。
- 身為**考慮與廖煒立合作的創業者或專案夥伴**，我想要**看到他做過什麼、哪些作品正在進行，以及怎麼聯絡他**，以達成**判斷是否發起合作**。
- 身為**廖煒立（作品多為半成品、部分作品要商業化的作者）**，我想要**一套固定的目錄、README 格式和公私分界規則**，以達成**可以分批上傳作品集中管理，而不洩漏要商業化的內容**。

## 2. PRD 六欄

| 欄位 | 內容 |
|---|---|
| 目的與效益 | 招募人員與合作對象難以在短時間判斷廖煒立的能力，因為作品分散、完成度不一；廖煒立自己也怕半成品拉低印象、商業內容被誤公開。本設計用「展示櫃 repo + 分區呈現 + 公私分界」同時解決這三件事（對應三句 User Story）。 |
| 範疇 In / Out | **In**：①`works/` 四個分類資料夾（web-apps、websites、music、research）；②三份 README 範本（公開作品 9 段、私有專案 10 段、商業展示卡）；③首頁 README 的「作品集」區（精選／製作中／靈感池三區）；④第一步實驗室公開展示卡；⑤MIT 授權；⑥`.gitignore` 公私分界規則；⑦把 PDF《個人網站與面試系統技術架構盤點》的內容整理進 `index.html` 的技術內容區。<br>**Out**：實際上傳各作品（第一批清單未定）；商業化作品的私人 repo 建立與遠端設定；音樂音檔上傳；自動產生 README 作品表的腳本；GitHub Pages 部署設定。 |
| 使用情境 | 招募人員：在公司電腦（桌機）或手機上，從履歷或 LinkedIn 點進 GitHub 首頁快速掃描，目的是決定要不要約面試（Claude 的判斷：裝置與時機）。合作對象：從推薦或搜尋點進來，想看作品與聯絡方式（Claude 的判斷）。廖煒立：在 Windows 桌機用 Claude Code 分批整理與上傳。 |
| 驗收標準 | 見下方 AC1–AC10。 |
| 限制條件 | GitHub 免費帳號：私人 repo 可用，Pages 需公開 repo。已 push 的內容幾乎收不回，因此商業內容必須在第一次 push 前就隔離。MIT 授權公開後不可撤回。預算 0。時程：沒有固定日期，分批上傳，第一批時間待定（使用者說法：「現在就可以上傳一些了」）。 |
| 優先順序 | 見下方優先順序表。 |

### 驗收標準

- **AC1**：repo 根目錄含 `README.md`、`LICENSE`、`.gitignore`、`index.html`、`works/`、`templates/`；`works/` 底下恰有 `web-apps`、`websites`、`music`、`research` 四個資料夾。
- **AC2**：執行 `git ls-files` 的結果不含 `.superpowers/`、`.remember/`、`.taste-skill/`、`dev-flow-package/`，也不含任何 `.env*`（`.env.example` 除外）。
- **AC3**：在 `git ls-files` 列出的檔案中搜尋「第一步」與「first-step」，只出現在 `README.md`、`.gitignore`（防護規則）、`works/research/first-step-lab/README.md` 與 `docs/superpowers/` 底下的設計、計畫、證據 `.md` 文件；且 `docs/` 底下只有 `superpowers/` 的 `.md` 檔，沒有 PDF、圖片或其他商業文件。（Claude 的判斷：判準用「檔名＋關鍵字」，並在 `.gitignore` 同時擋中英文檔名。）
- **AC4**：首頁 README 作品表中，每個作品都標有「構想／製作中／可 demo」其中一個狀態。
- **AC5**：「精選」區只在至少有一個達標作品時才顯示（沒有達標作品時整區隱藏，不放佔位列）；被放進「精選」區的作品，其 README 九段標題齊全，且「網站截圖」「線上體驗」「授權聲明」三段不是「尚未提供」。
- **AC6**：展示卡不含「技術架構」「環境設定」「資安與權限管理」「專案結構」任一段落標題，且「原始碼」欄為「不公開」。
- **AC7**：首頁 README 的前 25 行內有一句定位句，以及 Email 或 LinkedIn 連結；「作品集」標題出現在前 45 行內。（目前不符合：聯絡方式在檔案最下方，需調整。數字為 Claude 的判斷，用來對應「30 秒內看到定位、作品、聯絡方式」。）
- **AC8**：`index.html` 新增的技術內容區裡，每一項技術陳述都能在 `index.html` 的程式碼中找到對應；找不到的項目不寫，或明確標示「規劃中」。驗收證據是一張「陳述 → `index.html` 行號」的對照表。
- **AC9**：技術內容區在 375px 寬度下沒有水平捲軸；淺色、深色主題下文字與背景的對比都達 WCAG AA（一般文字 4.5:1）。
- **AC10**：技術內容區預設不寫任何效能數字（例如首次內容繪製時間）。只有在存在已部署的網址、且用 Lighthouse（mobile 設定）量測過時，才可寫入量測到的數字。

## 3. 反目標（Anti-goals）

- 就算目錄整齊，只要有任何商業化作品的內容、原始碼或金鑰進了公開 repo，就算失敗。
- 首頁不能讓半成品看起來像「做壞的作品」：製作中的作品要有明確狀態，而不是空白或壞連結。
- 不為了湊數量而放沒有說明的作品。

## 4. 使用者已決定的事

- 結構採方案 A：集中在這個 repo 當展示櫃；首頁分「精選／製作中／靈感池」三區（乙）。
- 公開作品 README 用使用者提供的 9 段格式；私有專案用 10 段格式，且只放私人專案。
- 商業化作品（第一步實驗室）：公開首頁露出展示卡，內容、原始碼、商業計畫書全部不公開。
- 公開作品授權不設限（Claude 對應為 MIT）。
- 音樂不放音檔（Claude 提議，使用者未反對）。
- `dev-flow-package/` 不公開。
- 要把 PDF 的技術內容放進 `index.html` 的技術內容區，**只寫網站目前實際有的內容**（使用者 2026-11-05 確認）：PDF 裡 `index.html` 還沒實作的項目（Apps Script 與 Google Sheets 寫入、`no-cors`、`ai-content-summary`、`<details>` FAQ、效能數字、「已驗證上線」）不寫，也不為了對齊 PDF 而修改網站功能。

## 5. Claude 的判斷（請檢查）

- 展示卡一句簡介：「協助容易拖延的人開始行動的網頁產品」。
- 展示卡放在 `works/research/`（商業研究）。
- MIT 持有人寫 Willy Liao（取自首頁 README）。
- 技術內容區放在 `index.html` 的工具箱區塊之後、FAQ 之前，做成獨立區塊，不直接內嵌 PDF 檔。
- 技術內容區的呈現：保留 PDF 的三層分層（前端、無伺服器、資料）與決策對照表，改寫成網頁段落與表格。

- 第 5 節各項，在使用者沒有反對之前視為採用。
- 這次的終點是**本機 commit，不 push、不開 PR**。範圍只含本設計列出的檔案；`assets/` 圖片刪除、`index.html` 既有的修改、`llms.txt`、`robots.txt`、`sitemap.xml` 不在這次 commit 內。（Claude 的判斷）
- 展示卡的必要欄位：作品名稱、狀態與分類與原始碼欄、一句簡介、合作聯絡指引、保留所有權利聲明。展示卡排除在 MIT 之外；其餘（含 `index.html`）依根目錄 MIT。（Claude 的判斷）
- 三份 README 範本的段落標題以 `templates/` 內檔案為準。
- 「精選」區在沒有達標作品前整區隱藏，首頁先只顯示「製作中」。
